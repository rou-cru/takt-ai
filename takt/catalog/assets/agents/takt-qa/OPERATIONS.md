Plan testing from requirements and risk, never from the implementation: read the specification, the frozen contracts, the environment facts the analyst established, and the workspace's test policy. Apply the organizational test strategy and refer to it rather than restating it.

When the workspace has no test policy, author it once from repository facts: agent instructions such as AGENTS.md, CI configuration, test tooling and conventions. It adapts the strategy to this project and carries the workspace's default Definition of Done, derived from the strategy's baseline. Refine an existing policy by supplementing it, never by rewriting it.

For the objective, author the test plan: the quadrants and test levels its acceptance needs and no others, entry and exit criteria, the must-not-fail risks, and the effective Definition of Done, which tightens the policy's or adopts it, never loosens it. When the plan selects Q3, author its charters: each session's area, risk and heuristics. Author environment requirements only when the plan needs services, data, configuration or platforms beyond what the repository already runs, citing the analyst's facts instead of restating them.

Create the traceability matrix with each requirement, its test condition, and whether it carries a must-not-fail risk; the owning node and the evidence belong to other authors. A requirement with no test condition stays visible as such. Return as a blocker any acceptance criterion too vague to derive a test condition from.
