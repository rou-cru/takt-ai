# PRD: Harness, Security, and Customization

## 1. Functional Requirements

### 1.1 Instructions and Deterministic Harness

| ID | Requirement |
| --- | --- |
| PR-HAR-1 | Deterministic guardrails in the harness back critical limits. |
| PR-HAR-2 | Permission profiles govern actions within tools, not only access to whole tools. A specialist MAY use an available tool for permitted actions while other actions through that same tool remain denied or approval-gated. |
| PR-HAR-3 | Mutating Git operations are concentrated in the orchestrator and the harness under explicit safeguards. |
| PR-HAR-4 | A textual instruction cannot make an agent exercise a capability that the harness does not expose or directly blocks at execution time. |
| PR-HAR-7 | A blocked action returns a deterministic visible denial naming the acting role, denied scope, and an available continuation call. Do not suggest a capability unavailable to that role: return the scope to the orchestrator when reassignment is required. A user-owned decision uses one scoped confirmation call. Text alone does not grant a blocked capability. |
| PR-HAR-8 | Every governed action resolves to **allowed**, **denied**, or **approval-gated** for the acting specialist. Approval-gating applies only to execution-boundary crossings and user-owned decisions. An approval-gated request MUST identify the acting agent, exact action, and rationale through the harness's deterministic question mechanism. |
| PR-HAR-9 | User approval MUST apply according to the persistence scope the user selects for the presented action. A one-time approval authorizes one immediate execution; a persistent approval, such as **Allow always**, MAY authorize later matching actions within the exact resource and policy scope presented to the user. No approval MAY silently broaden the action, resource, acting role, or governed scope beyond what the user accepted. |

### 1.2 Capability Taxonomy

| ID | Requirement |
| --- | --- |
| PR-HAR-10 | The harness enforces filesystem isolation and an explicit network allowlist for every role. The execution boundary is the security frontier: actions inside it run unattended under the acting role's profile, and crossing it requires scoped user authorization. Unavailable isolation is reported before the affected operation; it does not silently become unrestricted execution. |
| PR-HAR-11 | Shell authorization uses the executable, parsed arguments, flags, and effects, respecting quoting and command composition. Read-only inspection is unattended. Local dependency installation is unattended when its workspace delta is captured; uncaptured external effects require scoped authorization. Keywords inside arguments do not classify a command as an installation. Verification and quality-assurance shell writes are confined to scratch or isolated copies; planning writes are confined to its declared artifacts. |

### 1.4 Recovery Budgets, Admission, and Continuity

| ID | Requirement |
| --- | --- |
| PR-HAR-6 | The harness enforces declared recovery action and attempt allowances across the full recovery scope. Each distinct admitted attempt consumes one attempt; every recorded scoped action consumes action allowance. Duplicate requests consume neither twice. The last attempt may finish while actions remain. Exhaustion without demonstrated result forces abandonment, effective termination, and virtual restoration. A finite scoped exception adds allowance without erasing consumption. |
| PR-HAR-16 | Admission MUST reserve capacity indivisibly against the execution history: simultaneous requests cannot consume the same remaining slot. The concurrent-specialist ceiling is **4**, including admitted work pending launch, running work, and work pending termination that can still act. Pending admission to execution MUST NOT be reported as execution already started. |
| PR-HAR-17 | Repetition of the same admission, launch, or contest request MUST yield its recorded disposition without duplicating execution or limit consumption. A deliberate new attempt MUST be distinguishable from that repetition. After communication failure, an uncertain launch MUST be reconciled before any repeat that could duplicate execution; its capacity remains reserved until non-start or effective termination is established. A denied request consumes no execution slot, unplanned unit, or recovery attempt. |
| PR-HAR-18 | A cancellation, suspension, or backtracking request is not effective termination. The harness MUST NOT release execution capacity or exclusive ownership while that execution retains effective ability to act. Release requires recorded confirmation that it has ended or can no longer act; uncertainty retains the reservation. Termination and resolution controls MUST remain available even when the ceiling is full and MUST NOT require admitting another execution specialist. |
| PR-HAR-19 | Unplanned delegation is limited to **4 distinct admitted work units per session** across work classes, including focused repairs without plan coverage and work pending launch. Retries of the same unit do not add units; each newly admitted unit counts even if subsequently canceled or never launched. The fourth reaches the bound; a fifth uncovered unit MUST be denied until an enabling resolution is recorded. Committing a valid plan enables only work it covers, without erasing unplanned consumption. Stopping delegation does not reopen the allowance; sending an escalation is not a user decision. |
| PR-HAR-20 | At most **3 distinct contests per session** may be admitted, including upheld contests. The third consumes the last allowance; a fourth is denied absent a scoped user exception under `PR-HAR-22`. Transport duplicates do not count again; denied requests remain visible but consume no allowance. |
| PR-HAR-21 | Two consecutive failed recoveries of the same acceptance entity close autonomous recovery for that entity. Disposition follows PR-HAR-31. Only a finite scoped user exception permits recovery beyond the reached bound; unrelated progress does not clear its failure streak. |
| PR-HAR-22 | Limits and consumed budgets MUST survive runtime restart and specialist replacement within the same session; renaming work, changing its class, or redeclaring the same objective MUST NOT reset them. Declared continuity carries unresolved restrictions, active budgets, and failure streaks; it is not a fresh allowance for the same ongoing work. A user exception MUST identify the affected bound, objective/work scope, and a finite additional allowance expressed in that bound's own unit — attempts, actions, work units, or contests — after which it lapses, and be recorded before it enables further work. An exception MUST NOT be granted as a period of time. It does not erase consumption, authorize unrelated work, or replace any independent exact-action approval under `PR-HAR-9`. The default values in `PR-HAR-16`, `PR-HAR-19`..`21`, together with the admissible ceiling of each recovery declaration (**200 actions** and **3 attempts** per declaration; a declaration above its ceiling is denied), are canonical policy data. Adjustments replace those defaults without erasing consumption. |

### 1.5 Shell Capture and Configuration Custody

| ID | Requirement |
| --- | --- |
| PR-HAR-15 | The harness denies execution-specialist shell mutations whose effects the VFS cannot capture. It returns a capturable alternative or the scope to reassign, rather than executing unstaged. |
| PR-HAR-14 | Configuration mutation is granted only to the interface holder. Agents waiting underneath do not retain this capability while covered; it follows the active holder when the interface is lent or returned, including after a specialist fails. Internal-only agents cannot mutate configuration. |
| PR-CFG-1 | The harness deterministically identifies user-managed configuration and blocks any agent or update path from mutating or removing it outside an authorized scope. |

### 1.6 Arbitration of Interlocutor Transitions

| ID | Requirement |
| --- | --- |
| PR-HAR-23 | A switch, handoff, or abortion takes effect only as a structured harness event. Free-form text produced by an agent MUST NOT initiate, confirm, or complete a transition in either direction. The harness MUST validate that an event is well formed and originates from the agent that currently holds interactive control — the convening agent for a switch, the temporary holder for a handoff — and MUST reject an incomplete, invalid, or out-of-context request before any confirmation is presented, modifying no session and returning to the sender a deterministic error that names the valid continuation call. An abortion whose origin is an agent MUST be rejected the same way. The harness MUST NOT fabricate a successful outcome or mechanically rewrite what an agent produced; it rejects and returns the error. The harness alone owns session identities, their parent and child relationships, and which agent holds interactive control; an agent supplies only the event type, its operation key, the target specialist where applicable, the objective, and context references. |
| PR-HAR-24 | A completed result MUST be delivered through valid entry IDs recorded by the specialist in the session; chat or a filesystem copy alone is not a standard delivery. When an early close or failure coherently produces no result, the harness MUST NOT force a placeholder; any supplied result IDs MUST still be validated. A declared filesystem copy is optional: on handoff or abortion its existence MUST be reported alongside the envelope, but its absence MUST NOT block the first or any subsequent attempt. |
| PR-HAR-25 | The harness MUST validate the shape of the output envelope before delivering it: all four fields present, `Result` within its enumeration, valid use of explicit emptiness, and syntactically resolvable `ExtraArtifacts` references. A malformed envelope MUST be rejected with a deterministic error like any other invalid event. The harness MUST NOT arbitrate what has no verifiable answer: the correctness of envelope content is read by the receiving agent and validated by the user. Where no specialist remains to supply an envelope — a synthesized `Aborted`, or a synthesized `TechFault` after the temporary layer is destroyed without an accepted handoff — the harness MUST produce it with its optional fields empty, and MUST NOT reconstruct what happened. |
| PR-HAR-26 | Every transition request MUST carry an operation key that the harness uses as an idempotency key: replaying the same operation MUST return its recorded disposition without duplicating a session, a transition, or any side effect, and reusing that key with a different payload MUST be rejected. This holds for abortion as well: repeated against an already terminated specialist session it returns the same result and produces no new effect. |
| PR-HAR-27 | A transition is confirmed only once the target session is successfully activated. If activation fails, the current session MUST remain intact, the sender MUST receive a deterministic error, and no partially applied transition MAY remain. In an accepted switch, activation of the child session, transfer of interactive control, and the change of the user-facing view form a single observable transition, and the parent session stays alive. In an accepted handoff, delivery of the envelope to the receiving agent and termination of the specialist session form a single observable transition, and the view returns to the parent session. A rejection, a cancellation, and a freeform response leave the active state unchanged. Transitions are recorded as session-lifecycle facts in the execution history; no agent's account substitutes for that record. |
| PR-HAR-28 | The harness MUST durably record every `Result` of `Outraged` with its evidence, origin session, and emitting specialist, outside the write scope of any agent and beyond the reach of any memory-maintenance operation. The convening agent MUST receive the isolated incident and MUST NOT receive the accumulated aggregate or any threshold defined over it. |

### 1.7 Slice Admission and Correction

| ID | Requirement |
| --- | --- |
| PR-HAR-29 | Canonical admission policy sets finite unit limits per slice and per plan, a cumulative correction-dispatch limit per slice, an action allowance for that correction scope, and a QA-strengthening round limit. Admission counts every fix, reacceptance, and recritique in the scope across revisions. The first admitted authoring member consumes a declared QA round, not its siblings or duplicate callbacks. Committing, revising, or renaming a plan does not reset consumption. Invalid or missing limits deny affected admission with a configuration error naming the affected limit and the policy entry to correct. |
| PR-HAR-30 | Recovery, QA rounds, and correction budgets bind to persisted acceptance-entity identities. The owner validates identity and allowance atomically with admission. A planned dispatch selects a declared unit ID; a mismatch returns available planned identities and requires explicit selection or a new-unit declaration. |
| PR-HAR-31 | At a reached bound, the harness prevents further consumption of the exhausted allowance. A deterministic policy then selects either an autonomous reroute within remaining authorized work or a closing report recording unmet criteria. The user is consulted only when the user's explicit policy requires it. Close, reporting, and effective termination remain available. A new route cannot reset the exhausted scope. |
