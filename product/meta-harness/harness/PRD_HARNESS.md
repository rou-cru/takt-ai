# PRD: Harness, Security, and Customization

**Actual implementation progress: 78%** — 29 own requirements: 18 complete, 9 partial, 2 not integrated. Gaps: configuration custody is granted by static role rather than following the interlocutor-stack holder, and no mechanism attributes a user-instructed mutation to the user. Interlocutor transitions have no idempotency key, an agent-invoked abort is stamped as user-originated, envelope validation covers shape only, a failed activation can leave a partial transition, and an Outraged result has no isolated durable record.

## 1. Problem

Relying exclusively on semantic instructions in natural language leaves the system vulnerable to attention degradation, hallucinations, or misinterpretation. Takt requires a deterministic technical harness that guarantees no agent exceeds its authorized capabilities, while protecting user customizations and configurations without restriction.

## 2. Functional Requirements

### 2.1 Instructions and Deterministic Harness

| ID | Requirement |
| --- | --- |
| PR-HAR-1 | Takt defines operational expectations through clear semantic instructions and backs critical limits with deterministic guardrails in the harness. |
| PR-HAR-2 | Permission profiles govern actions within tools, not only access to whole tools. A specialist MAY use an available tool for permitted actions while other actions through that same tool remain denied or approval-gated. |
| PR-HAR-3 | High-impact capabilities are concentrated in specific role classes under explicit safeguards: mutating Git operations in the orchestrator (`PR-CRW-5`) and configuration mutation in the active interface holder (`PR-HAR-14`). |
| PR-HAR-4 | A textual instruction cannot make an agent exercise a capability that the harness does not expose or directly blocks at execution time. |
| PR-HAR-5 | Deterministic restrictions function as a safety net; instruction design guides the agent to operate fluidly without repeatedly colliding against harness blocks. |
| PR-HAR-7 | Harness limits determine which actions are technically executable, not which instruction has normative authority. A blocked action produces a visible and deterministic result that the agent cannot evade and that names the call the agent continues with. Where the way on is a decision that belongs to the user, the result says to ask them, and the harness carries that decision out in one call. |
| PR-HAR-8 | Every governed action resolves to **allowed**, **denied**, or **approval-gated** for the acting specialist. An approval-gated request MUST identify the acting agent, exact action, and rationale through the harness's deterministic question mechanism. |
| PR-HAR-9 | User approval MUST apply according to the persistence scope the user selects for the presented action. A one-time approval authorizes one immediate execution; a persistent approval, such as **Allow always**, MAY authorize later matching actions within the exact resource and policy scope presented to the user. No approval MAY silently broaden the action, resource, acting role, or governed scope beyond what the user accepted. |

### 2.2 Capability Taxonomy

| ID | Requirement |
| --- | --- |
| PR-HAR-10 | Governed capabilities: filesystem mutation (transactionally staged via VFS), Git mutation (governed per role), and configuration mutation (reserved to the active user-facing interface holder). Filesystem read is available to all specialists but remains subject to exclusive file ownership during concurrent work; network access is unrestricted for all specialists. |
| PR-HAR-11 | Shell command execution is available to the orchestrator and specialists under their OpenCode permission profiles. Orchestrator shell uses native OpenCode permissions and is not forced through VFS. Verification-class shell does the same, with native edit denied: the class is bound by its conduct not to modify the project. For other specialists, a command with effects outside the workspace that VFS cannot capture is approval-gated (`PR-HAR-8`, `PR-HAR-9`): the request identifies the exact command and approval authorizes that one execution. Unrestricted network reachability (`PR-HAR-10`) does not exempt a specialist command from this rule. Specialist workspace mutations follow `PR-HAR-15`; Git mutation follows `PR-VFS-GIT-1` and `PR-VFS-GIT-3..5`. |

### 2.3 Customization and Conflict Management

| ID | Requirement |
| --- | --- |
| PR-CFG-2 | When a Takt update conflicts with an existing customization, the harness deterministically detects the incompatibility and suspends unilateral application. |
| PR-CFG-3 | A mutation an agent performs on the user's explicit instruction is attributed to the user, not to Takt. Only the product's own deterministic operations — installation, update, projection, and harness enforcement — are Takt operations. A user-instructed change whose target happens to be Takt's installed configuration remains a user change: the target does not convert it into a Takt operation, and it is treated under the same rules as any other user modification. |

### 2.4 Recovery Budgets, Admission, and Continuity

| ID | Requirement |
| --- | --- |
| PR-HAR-6 | For a recovery declared under `PR-ORQ-13`, the harness MUST enforce the recorded action and attempt budgets over the entire recovery scope, including retries and associated work, without resetting either budget. The two are distinct and both binding: attempts bound how many times the recovery is retried, actions (`PR-OBS-PRG-2`) bound how much work fits inside the declared scope. Each distinct admitted execution attempt in that scope consumes an attempt; duplicate requests do not. Every recorded action within the scope consumes action allowance, whichever attempt performs it. Admitting the last permitted attempt bars another admission but lets that attempt finish and present evidence while action allowance remains. When all admitted attempts have finished without the declared result and no attempt allowance remains, or when the action budget is exhausted first, the harness MUST force backtracking without renewed orchestrator approval (`PR-DAG-TMP-5`, `PR-VFS-STG-6`). At exhaustion, missing evidence is not success. It MUST NOT invent an absent result, budget, or recoverable point, nor promise reversible recovery without the prerequisites of `PR-ORQ-13`. The user's exception on the exhausted bound for that objective (`PR-HAR-22`) lifts the abandonment: the scope reopens with the allowance beside its recorded consumption and its staged work intact. Dropping the scope is its restoration (`PR-VFS-STG-6`). |
| PR-HAR-16 | Admission MUST reserve capacity indivisibly against the DAG projection: simultaneous requests cannot consume the same remaining slot. The first-release concurrent-specialist ceiling is **4**, including admitted work pending launch, running work, and work pending termination that can still act (`PR-HAR-18`). Pending admission to execution MUST NOT be reported as execution already started. The orchestrator selects work; enforcement does not select among routes or judge prerequisites (`PR-DAG-AUT-1`). |
| PR-HAR-17 | Repetition of the same admission, launch, or contest request MUST yield its recorded disposition without duplicating execution or limit consumption. A deliberate new attempt MUST be distinguishable from that repetition. After communication failure, an uncertain launch MUST be reconciled before any repeat that could duplicate execution; its capacity remains reserved until non-start or effective termination is established. A denied request consumes no execution slot, unplanned unit, or recovery attempt. |
| PR-HAR-18 | A cancellation, suspension, or backtracking request is not effective termination. The harness MUST NOT release execution capacity or exclusive ownership while that execution retains effective ability to act. Release requires recorded confirmation that it has ended or can no longer act; uncertainty retains the reservation. Termination and resolution controls MUST remain available even when the ceiling is full and MUST NOT require admitting another execution specialist. |
| PR-HAR-19 | Unplanned delegation is limited to **4 distinct admitted work units per session** across work classes, including focused repairs without plan coverage and work pending launch. Retries of the same unit do not add units; each newly admitted unit counts even if subsequently cancelled or never launched. The fourth reaches the bound and requires resolution under `PR-ORQ-20`; a fifth uncovered unit MUST be denied until an enabling resolution is recorded. Committing a valid plan enables only work it covers, without erasing accumulated unplanned history. Stopping delegation does not reopen the allowance; sending an escalation is not a user decision. |
| PR-HAR-20 | At most **3 distinct contests per session** may be admitted under `PR-DAG-TMP-7`, including upheld contests. The third consumes the last allowance; a fourth is denied absent a scoped user exception under `PR-HAR-22`. Transport duplicates do not count again; denied requests remain visible but consume no allowance. |
| PR-HAR-21 | **2 consecutive failed recoveries of the same objective** require escalation under `PR-ORQ-13`. The second failure closes autonomous recovery for that objective; another recovery MUST NOT be admitted until an enabling user decision is recorded. Only a demonstrated successful recovery of that objective breaks its failure streak; unrelated progress or a different specialist does not. |
| PR-HAR-22 | Limits and consumed budgets MUST survive runtime restart and specialist replacement within the same session; renaming work, changing its class, or redeclaring the same objective MUST NOT reset them. Declared continuity (`PR-DAG-USE-1`) carries unresolved restrictions, active budgets, and objective failure history; it is not a fresh allowance for the same ongoing work. A user exception MUST identify the affected bound, objective/work scope, and a finite additional allowance expressed in that bound's own unit — attempts, actions, work units, or contests — after which it lapses, and be recorded before it enables further work. An exception MUST NOT be granted as a period of time. It does not erase consumption, authorize unrelated work, or replace any independent exact-action approval under `PR-HAR-9`. The default values in `PR-HAR-16`, `PR-HAR-19`..`21`, together with the admissible ceiling of each recovery declaration under `PR-ORQ-13` (**200 actions** and **3 attempts** per declaration; a declaration above its ceiling is denied), are canonical policy data; the crew's prose receives them at install from that policy, never as a second copy, and an adjusted value under `PR-TUI-25` replaces the default in both. |

### 2.5 Shell Capture and Configuration Custody

| ID | Requirement |
| --- | --- |
| PR-HAR-15 | For execution specialists, shell execution MUST NOT be a path around the VFS. Their workspace file mutations produced by shell MUST be captured and applied within the VFS layer exactly as mutations issued through file tools (`PR-VFS-STG-1`), and MUST NOT reach the physical workspace ahead of consolidation. A specialist mutation that cannot be captured MUST be denied rather than executed unstaged. This requirement does not restrict the orchestrator: its native filesystem and shell operations follow its OpenCode permission profile and are not required to pass through VFS. |
| PR-HAR-14 | Configuration mutation is granted only to the current top agent in the user-facing interlocutor stack. Agents waiting underneath do not retain this capability while covered; it follows the active holder when the interface is lent or returned, including after a specialist fails. The session's initial agent may be the Orchestrator or a directly invoked Specialist. Internal-only agents cannot mutate configuration. |
| PR-CFG-1 | The harness deterministically identifies user-managed configuration and blocks any agent or update path from mutating or removing it outside an authorized scope. |

### 2.6 Arbitration of Interlocutor Transitions

| ID | Requirement |
| --- | --- |
| PR-HAR-23 | A switch, handoff, or abortion (`IR-19`) takes effect only as a structured harness event. Free-form text produced by an agent MUST NOT initiate, confirm, or complete a transition in either direction. The harness MUST validate that an event is well formed and originates from the agent that currently holds interactive control — the convening agent for a switch, the temporary holder for a handoff — and MUST reject an incomplete, invalid, or out-of-context request before any confirmation is presented, modifying no session and returning a deterministic error to the sender. An abortion whose origin is an agent MUST be rejected the same way (`IR-24`). The harness MUST NOT fabricate a successful outcome or mechanically rewrite what an agent produced; it rejects and returns the error. The harness alone owns session identities, their parent and child relationships, and which agent holds interactive control; an agent supplies only the event type, its operation key, the target specialist where applicable, the objective, and context references. |
| PR-HAR-24 | A completed result MUST be delivered through valid Engram IDs recorded by the specialist in the session; chat or a filesystem copy alone is not a standard delivery. When an early close or failure coherently produces no result, the harness MUST NOT force a placeholder; any supplied result IDs MUST still be validated. A declared filesystem copy is optional: on handoff or abortion its existence MUST be reported alongside the envelope, but its absence MUST NOT block the first or any subsequent attempt. |
| PR-HAR-25 | The harness MUST validate the shape of the output envelope before delivering it: all four fields present, `Result` within its enumeration, valid use of explicit emptiness, and syntactically resolvable `ExtraArtifacts` references (`IR-22`). A malformed envelope MUST be rejected with a deterministic error like any other invalid event. The harness MUST NOT arbitrate what has no verifiable answer: the correctness of envelope content is read by the receiving agent and validated by the user. Where no specialist remains to supply an envelope — a synthesized `Aborted`, or a synthesized `Tech Fault` after the temporary layer is destroyed without an accepted handoff — the harness MUST produce it with its optional fields empty, and MUST NOT reconstruct what happened. |
| PR-HAR-26 | Every transition request MUST carry an operation key that the harness uses as an idempotency key: replaying the same operation MUST return its recorded disposition without duplicating a session, a transition, or any side effect, and reusing that key with a different payload MUST be rejected. This holds for abortion as well: repeated against an already terminated specialist session it returns the same result and produces no new effect. It is the discipline `PR-HAR-17` applies to admission, launch, and contest requests, applied to transition events. |
| PR-HAR-27 | A transition is confirmed only once the target session is successfully activated. If activation fails, the current session MUST remain intact, the sender MUST receive a deterministic error, and no partially applied transition MAY remain. In an accepted switch, activation of the child session, transfer of interactive control, and the change of the user-facing view form a single observable transition, and the parent session stays alive. In an accepted handoff, delivery of the envelope to the receiving agent and termination of the specialist session form a single observable transition, and the view returns to the parent session. A rejection, a cancellation, and a freeform response leave the active state unchanged (`IR-21`). Transitions are recorded as session-lifecycle facts in the execution history (`PR-DAG-REP-2`), which is what answers whether a transition occurred; no agent's account substitutes for it. |
| PR-HAR-28 | The harness MUST durably record every `Result` of `Outraged` (`IR-23`) with its evidence, origin session, and emitting specialist, outside the write scope of any agent and beyond the reach of any memory-maintenance operation (`MEM-OPS-1`). The convening agent MUST receive the isolated incident, so that it can recognize its own drift and correct course while the incident remains isolated, and MUST NOT receive the accumulated aggregate, the historical record, or any threshold defined over them: an agent that knows the metric can optimize against it and suppress the signal instead of its cause. |

## 3. Failure Behavior

| Situation | Expected Behavior |
| --- | --- |
| User denies an approval-gated request | The denial applies to that attempt. The agent receives a deterministic, visible result and proceeds differently; the denial does not backtrack the work unit and is not re-escalated to the user. |
| An agent attempts a denied action | Blocked at execution time with a visible deterministic result the agent cannot evade (`PR-HAR-4`, `PR-HAR-7`). |
| Two simultaneous admissions compete for the fourth slot | At most one is admitted; the other is visibly denied while capacity is exhausted. The reservation counts before launch (`PR-HAR-16`). |
| Admission or launch request is delivered twice | The same disposition is returned; one execution and one consumption, not two (`PR-HAR-17`). |
| Communication fails after a possible launch | Reconcile first; do not launch a replacement or release its reservation on uncertainty (`PR-HAR-17`). |
| Cancellation requested while a specialist can still act | Ownership and its slot remain reserved, including during suspension; release follows effective termination, not the request (`PR-HAR-18`). |
| Last recovery attempt admitted | It may complete with evidence while action allowance remains; no extra attempt is admitted. Failure or an exhausted action budget forces backtracking (`PR-HAR-6`). |
| Fourth unplanned unit admitted; fifth requested | Fourth may finish; fifth is denied pending an enabling resolution. A stop declaration or unanswered escalation does not reopen delegation (`PR-HAR-19`). |
| Three contests upheld; fourth requested | Fourth is denied; successful contests consume the same allowance (`PR-HAR-20`). |
| Second consecutive recovery fails for the same objective | Escalation is required; renaming work or restarting the runtime cannot enable a third recovery (`PR-HAR-21`..`22`). |
| User grants a scoped limit exception | Only that finite scope is enabled; an independently governed action still resolves through its own policy or approval decision (`PR-HAR-9`, `PR-HAR-22`). |
| A Takt update conflicts with a user customization | Unilateral application is suspended and the choice is presented to the user (`PR-CFG-2`, `IR-12`). |
| An agent emits an abortion | Rejected with a deterministic error; no session changes and no confirmation is presented (`PR-HAR-23`, `IR-24`). |
| Standard handoff arrives without an Engram result | Rejected; a filesystem copy cannot substitute for the result. Optional copy absence is reported but never blocks a handoff (`PR-HAR-24`). |
| Output envelope is structurally invalid | Rejected with a deterministic error; the harness neither repairs it nor judges its content (`PR-HAR-25`). |
| Same transition operation key replayed | The recorded disposition is returned; no duplicate session, transition, or side effect (`PR-HAR-26`). |
| Target session activation fails mid-transition | Nothing remains partially applied; the current session stays intact and the sender receives the error (`PR-HAR-27`). |
| Temporary layer is destroyed without an accepted handoff | Control returns to the convening agent with a synthesized `Tech Fault` and empty optional fields; nothing is reconstructed (`PR-HAR-25`, `IR-23`). |
| Deterministic confirmation is unavailable during a specialist session | The specialist reports the problem instead of improvising a transition; user abortion remains the exit (`IR-20`, `PR-HAR-23`). |
| A result attributes cause to the convening agent | It receives that isolated incident only, never the aggregate or any threshold over it (`PR-HAR-28`). |
