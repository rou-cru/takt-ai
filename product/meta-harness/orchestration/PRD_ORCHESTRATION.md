# PRD: Orchestration and Crew Direction

**Actual implementation progress: 57%** — 28 own requirements: 5 complete, 22 partial, 1 not integrated. The concurrency ceiling and admission accounting the orchestrator's DAG execution must respect (PR-ORQ-10) is `takt/dispatch/dispatch.go`'s real admission gate, not a self-imposed limit. Exclusive ownership is now inspectable and preassignable through explicit orchestrator claim controls; atomic scope acquisition returns exact owner evidence on refusal, prior-session claims persist until explicit orchestrator release, and workspace reads are subject to the same ownership rule (PR-ORQ-18, PR-VFS-COL-4..6). Handover through switch/handoff is a harness-structured event, not an arbitrary decision (PR-ORQ-6, `takt/dispatch/interlocutor.go`). That SDD is the first-release framework and the execution DAG is the orchestrator's own compiled strategy rather than a framework artifact (PR-ORQ-19) is the architecture as built, not aspiration. The unplanned-delegation bound forcing a plan commitment (PR-ORQ-20) closes in production through `dispatch_commit` and `PR-HAR-19`'s bound. Recovery declaration/closure (PR-ORQ-13) and exclusive-ownership's own request path reach production, but the judgment governing when to use them, milestone calibration (PR-ORQ-12), and resuming direction after a lent session hands the interface back (PR-ORQ-24..28) all remain prompt-only judgment layered on real mechanism — capped at partial by convention regardless of prompt quality. `PR-ORQ-23` — why `takt-invariant-planning` and `takt-sdd-workflow` use different edge logic (document consumption vs. file collision) — has no stated design rationale anywhere and is not integrated by either lever.

## 1. Problem

Orchestration coordinates specialist work toward the user’s goal, manages dependencies and concurrent execution, and escalates decisions outside its delegated scope.

## 2. Functional Requirements

### 2.1 Crew Direction and Supervision

| ID | Requirement |
| --- | --- |
| PR-ORQ-1 | The orchestrator receives the goal and directives from the user, assimilating them as the guiding principle for the entire session. |
| PR-ORQ-2 | The orchestrator decomposes the goal vertically: first into objectives, then into coherent work units whose tasks and files produce functional progress for one specialist rather than disconnected edits. |
| PR-ORQ-3 | The orchestrator continuously supervises the consistency of technical progress against the agreed goal. |
| PR-ORQ-4 | The orchestrator has autonomy to resolve minor technical problems, implementation divergences, and tactical adjustments without requiring constant user intervention. |
| PR-ORQ-5 | The orchestrator detects substantial deviations, course ambiguities, or unforeseen high-risk situations and escalates them in time. |
| PR-ORQ-6 | Any handover in technical coordination or agent collaboration is governed by predefined explicit mechanisms, not by unverifiable arbitrary decisions. |
| PR-ORQ-7 | Parallel work requires explicit, exclusive file ownership: two concurrently active agents MUST NOT operate on the same file in any mode, including reading. The orchestrator first assigns naturally independent codebase objectives to different agents. When a dependency can be removed by a predefined contract, the orchestrator supplies that contract to both agents before dispatch so each can proceed in separate files without inspecting or waiting for the other's implementation. |
| PR-ORQ-8 | Every handoff includes verifiable facts, result, and limits; if evidence is insufficient to establish continuity, the orchestrator escalates and does not infer it. |
| PR-ORQ-9 | The orchestrator serializes dependent work only when independence cannot be achieved through separate file scopes and predefined contracts, including when the files each agent must access cannot be bounded confidently. |
| PR-ORQ-10 | A DAG execution MUST respect the concurrent-specialist ceiling and admission accounting owned by `PR-HAR-16`..`18`. Additional ready work waits for capacity even when no functional dependency requires serialization. The orchestrator MUST NOT lower the ceiling out of caution. The harness counts the projection, not a second in-flight record; it does not schedule work. |
| PR-ORQ-11 | The orchestrator and participating specialists proactively seek safe concurrency, while the orchestrator remains directly accountable for the DAG's correctness and execution. |
| PR-ORQ-12 | A milestone requires a verified functional state but is not produced by every functional intermediate state. Unless the user defines checkpoints in advance, the orchestrator calibrates milestones according to the expected outcome, impact, work-unit scope, DAG topology, and whether completed work represents solid usable or visible progress toward the goal. |
| PR-ORQ-13 | When the DAG encounters an unplanned condition, the orchestrator MAY attempt autonomous reversible recovery only after declaring a binary expected result, an action budget (`PR-OBS-PRG-2`), an attempt budget, an identified prior recoverable point, and explicit work scope. The two budgets are distinct and both required — attempts bound how many times it retries, actions bound how much work the recovery scope may consume — and the orchestrator declares the action budget because the effort a scope demands in steps is what it can estimate, while how long that takes is not. The result MUST be demonstrable before consolidation of the deltas in that scope; executable post-consolidation acceptance is not such a result (`PR-VFS-CSL-6`). The reversible promise is confined to unconsolidated VFS state (`PR-VFS-STG-6`), not external effects. Failure to demonstrate the result within the budget requires abandoning that scope, effective termination, and confirmed restoration, preserving unrelated progress (`PR-HAR-6`, `PR-HAR-18`). Repeated failed recovery of the same objective requires escalation at the bound in `PR-HAR-21`; sending the escalation does not authorize another attempt. The orchestrator MUST present the evidence and alternatives under `IR-10` and await the user decision governing continuation (`IR-11`). |
| PR-ORQ-18 | The orchestrator inspects existing claims and requests exclusive ownership of the file set declared in the work unit's contract before dispatch. The harness atomically validates that requested scope against held and pending claims and refuses conflicts with the exact path, target, and existing owner agent/session/unit; it does not choose assignments or releases. Requester and target identities are harness-owned, not model-provided. Claims persist across `FS.Close`: a prior-session owner is not implicitly stale and MUST be inspected and explicitly revoked by the orchestrator before reuse. No age-based expiry, automatic transfer, cleanup, regrouping, or scheduling is permitted. Active-session confirmation UI/handshake belongs to the plugin. Release on completion, failure, backtracking, or interruption requires effective termination under `PR-HAR-18`; requesting cancellation or suspension alone never releases ownership. A specialist needing a file outside its declared set MUST request an extension from the orchestrator, which grants it only if no other active or reserved owner holds that file; accessing an undeclared file without an extension is a collision. |
| PR-ORQ-21 | Planning lanes that generate invariants ahead of implementation are ordered by consumption: a lane is dispatched only once every output it consumes from another lane in the session has been returned and its gate has passed, and lanes whose inputs are all available run concurrently within `PR-ORQ-10`. No lane has a fixed position (`PR-ORQ-16`); a chain, a fan-out, a diamond, or independent lanes are each correct when they match what is consumed. |
| PR-ORQ-22 | Each planning lane runs with the user or autonomously, as the user's instruction sets it and, absent one, interlocutors with the user and internal lanes autonomously, so a mix is a valid hybrid. The gate of an autonomous lane is the orchestrator's check that the documents at that level do not contradict one another or the invariants above them; on a contradiction the orchestrator decides which document stands and re-dispatches only the other lane to align its own. |
| PR-ORQ-23 | The bias toward concurrency of `PR-ORQ-7`, `PR-ORQ-9` and `PR-ORQ-11` governs work on the codebase, where a predefined contract stands in for a pending output; a planning lane's pending output cannot be predefined, because producing it is the lane's work. |

> **Example — PR-ORQ-7.** A contract can give one agent a function to implement and another its use in entirely separate files. Both receive the same function name, parameters, inputs, outputs, and expected behavior; neither needs to access the other's files to proceed.

### 2.2 Resuming Direction After a Lent Interface

| ID | Requirement |
| --- | --- |
| PR-ORQ-24 | The convening agent's context was frozen at the moment of the switch, while the temporary holder may have produced new decisions and documents. Before proceeding it MUST catch up from two distinct and non-interchangeable sources: what happened during the lent session is provided by the harness, the sole authority over the transition and its record (`PR-HAR-27`, `PR-DAG-REP-2`), and the convening agent MUST NOT reconstruct it by search nor infer it from the envelope; what remains in effect as knowledge is provided by memory and the artifacts, queried by topic. Conflating the two is a failure: recovering the course of a session through semantic retrieval yields a plausible narrative in place of a fact. When it cannot establish what happened, it MUST declare that and consult the user, and MUST NOT fill the gap with what seems plausible. |
| PR-ORQ-25 | With an envelope that meets its contract (`IR-22`), the convening agent MUST validate the envelope, read `AdditionalContext`, interpret `Result` as the attribution of cause it is (`IR-23`), and relate both to the objective's state and to any new requirements before it proceeds. It decides how deeply to inspect `ExtraArtifacts` from the result, the context, the objective, and the risk: it MUST NOT set them aside without understanding them, and MUST NOT read them all mechanically. When available evidence does not let it decide, it tells the user what needs investigation or asks how to proceed (`IR-10`). |
| PR-ORQ-26 | An envelope that does not meet its contract withdraws the convening agent's licence to rely on it: it MUST verify artifacts, paths, memory entries, and context firsthand instead of trusting the summary or the declared references, because an invalid envelope may indicate a degraded or erratic temporary holder. |
| PR-ORQ-27 | Facing any anomalous situation on resumption, the convening agent MUST assess the scale of the situation, consult the user before assuming anything when evidence is missing, explain the impact and propose how to handle it when the situation is recognized, confirm the procedure with the user before advancing (`IR-11`), and obtain a new deterministic confirmation for any further switch (`IR-20`). A `Tech Fault` MUST be taken to the user for a decision on how to proceed; the convening agent MUST NOT advance on its own because the problem appears trivial. |
| PR-ORQ-28 | An `Aborted` result arrives with no content to interpret: the convening agent MUST consult the user rather than infer or reconstruct what happened, MUST NOT attribute fault to the temporary holder or to itself, and MUST NOT let it feed any reasoning about degradation (`IR-23`). An `Outraged` result attributes the cause to the convening agent itself: it receives that isolated incident in order to recognize its own drift and correct course while the incident remains isolated, and it has no access to the accumulated record or to any threshold over it (`PR-HAR-28`). |

### 2.3 Workflow Frameworks

| ID | Requirement |
| --- | --- |
| PR-ORQ-14 | A workflow framework is a supported reference for the software-development happy path, providing planning artifacts, theoretical support for decisions, and a shared way to understand progress. It is never the universal route for every kind of work. |
| PR-ORQ-15 | A framework's planning artifacts reduce uncertainty and reveal whether work is still being planned, is ready for implementation, or has produced verifiable results. Their availability informs orchestration decisions without imposing a predetermined route. |
| PR-ORQ-16 | No framework imposes rigid phases, a fixed linear sequence, or phase ownership by particular agents. Any linear progression is circumstantial and must follow real dependencies rather than the framework's nominal order. |
| PR-ORQ-17 | A framework MAY recommend suitable specialists for a given objective, but the orchestrator remains responsible for selecting the actual execution route and participants according to the goal and current evidence. |
| PR-ORQ-19 | The workflow framework shipped in the first release is spec-driven development (SDD). Its planning artifacts are the specification with its acceptance criteria and the frozen interface contracts. These artifacts are the planning inputs referenced by `PR-ORQ-15` and part of the reference invariants of `PR-VFS-CSL-3`. The execution DAG is not among them: it is the orchestrator's own strategy, compiled by the orchestrator from those artifacts and mutable by it throughout execution (`PR-ORQ-17`, `PR-CRW-5`, `PRD_DAG`). |
| PR-ORQ-20 | The active workflow determines whether and when the orchestrator MUST commit an execution plan; there is no unconditional baseline requirement for all delegated implementation outside that workflow. Without such a requirement, accumulated delegation remains bounded by `PR-HAR-19`. On reaching that bound the orchestrator MUST commit a valid plan covering intended work, stop that delegation and use existing results, or escalate because it cannot identify a route. Only plan coverage or an enabling scoped user decision permits further affected delegation; stopping and requesting a decision do not themselves enable it. The additional user acceptance required after concurrent editing without a plan remains governed by `PR-HAR-19`. Plan commitments and resolutions are recorded under `PR-DAG-MUT-1` and `PR-DAG-MUT-10`. |

> **Failure behavior — recovery and commitment.** An unmet result on the last attempt causes backtracking, not an automatic retry. A result that can only be checked after materialization cannot be the stopping criterion for reversible recovery; failed post-consolidation acceptance requires forward correction (`PR-VFS-CSL-6`). After the repeated-failure bound, an unanswered escalation leaves further recovery of that objective blocked. Stopping unplanned delegation permits use of existing results, not a new batch under a renamed class (`PR-HAR-19`..`22`).
