# PRD: Orchestration and Crew Direction

## 1. Functional Requirements

### 1.1 Crew Direction and Supervision

| ID | Requirement |
| --- | --- |
| PR-ORQ-1 | The orchestrator receives the goal and directives from the user; they guide the entire session. |
| PR-ORQ-2 | The orchestrator decomposes product work into functional vertical slices traced to user stories. A bounded change uses one execution specialist; an integrated feature uses a slice; a new product starts with an executable skeleton and expands story by story. A unit may span layers. Split work only for independently deliverable contracts or bounded context, not to create one delegation per layer. |
| PR-ORQ-3 | The orchestrator continuously supervises the consistency of technical progress against the agreed goal. |
| PR-ORQ-4 | The orchestrator has autonomy to resolve minor technical problems, implementation divergences, and tactical adjustments without requiring constant user intervention. |
| PR-ORQ-5 | The orchestrator detects substantial deviations and course ambiguities, resolves them within its delegated authority, and escalates only what meets `IR-18`. |
| PR-ORQ-6 | Any handover in technical coordination or agent collaboration is governed by predefined explicit mechanisms. |
| PR-ORQ-7 | Parallel execution requires disjoint declared write scopes, settled shared contracts, and compatible environments. The orchestrator does not create artificial dependencies to serialize independent work. |
| PR-ORQ-8 | Every handoff includes verifiable facts, result, and limits; if evidence is insufficient to establish continuity, the orchestrator establishes it firsthand from artifacts and the execution history and does not infer it. |
| PR-ORQ-10 | Ready independent work runs within harness admission bounds; excess work queues without artificial prerequisites. The orchestrator chooses work. |
| PR-ORQ-11 | The orchestrator remains directly accountable for the DAG's correctness and execution. |
| PR-ORQ-12 | The orchestrator identifies meaningful functional milestones from accepted results and the user's expected outcome. Milestone naming does not alter acceptance. |
| PR-ORQ-34 | Each slice has one independent acceptance assignment covering its integrated result, not one per author or wave. It runs only missing or invalidated checks when acceptance repeats. Its consistency check replaces an integration-only coordination node with no executable evidence. |
| PR-ORQ-35 | At each accepted slice, the orchestrator evaluates the result and selects the next work. With user participation it explains how to try the result and asks whether to refine or continue. Corrections needed to satisfy current requirements remain in scope and consume the slice budget; they revise the technical plan without reopening unchanged stories. New capabilities and improvements enter the backlog unless the user redirects the work. A user-originated change to observable requirements modifies the story and its affected derived artifacts. |
| PR-ORQ-36 | Ready slices meeting `PR-ORQ-7` may execute concurrently. Selection takes prerequisites first, then the highest user priority, then declared plan order; a scoped user instruction on concurrency prevails. |
| PR-ORQ-13 | Before reversible recovery, the orchestrator declares the binary result, persistent acceptance entity, scope, action allowance, and attempt allowance, and demonstrates the result on unconsolidated work before release. Effects outside VFS are not reversible recovery. |
| PR-ORQ-18 | Before dispatching a VFS-governed writer, the orchestrator inspects claims and requests the unit's complete write scope. Claims persist until explicit resolution; age does not authorize reuse. The harness owns instance identities and returns exact ownership conflicts. Release requires effective termination. A specialist needing additional write paths returns those paths for scope reassignment; read-only exploration does not expand write scope. |
| PR-ORQ-33 | A fix unit repairs one localized defect or one identical mechanical pattern and supplies a regression check. It does not diagnose. The verifier supplies an executable reproduction and location where known; unresolved causes go to analyst. Correlated or intertwined repairs requiring implementation judgment go to dev. All corrections consume the affected slice's budget. |
| PR-ORQ-21 | Planning lanes that generate invariants ahead of implementation are ordered by consumption: a lane is dispatched only once every output it consumes from another lane in the session has been returned and its gate has passed, and lanes whose inputs are all available run concurrently within `PR-ORQ-10`. No lane has a fixed position; a chain, a fan-out, a diamond, or independent lanes are each correct when they match what is consumed. |
| PR-ORQ-37 | General requests establish concrete stories for the next executable slice before consuming lanes start. In autonomous mode, PM and design use minimal explicit, testable assumptions compatible with the goal. Uncertainty about value or conflicting user requirements returns to the user; routine technical uncertainty does not block story formalization. |
| PR-ORQ-22 | Planning follows the user's participation mode. The architect performs a bounded coherence review comparing only changed artifacts and their affected invariants, returning inconsistencies by entry ID. The orchestrator resolves conflicts within its delegated authority and re-dispatches the owner of the lower artifact. Conflicting user stories require a user decision. Routine revisions do not require complete artifact rereads. |
| PR-ORQ-38 | A specialist that needs a global query beyond its declared scope receives it from a read-only exploration unit with a bounded scope, dispatched by the orchestrator. |
| PR-ORQ-23 | A predefined code contract can permit concurrency without awaiting another implementation. A planning lane's pending output is not available until produced. |

### 1.2 Resuming Direction After a Lent Interface

| ID | Requirement |
| --- | --- |
| PR-ORQ-24 | The convening agent's context stays frozen from the switch while the temporary holder may produce new decisions and documents. Before proceeding it MUST catch up from two distinct and non-interchangeable sources: what happened during the lent session is provided by the execution history, and the convening agent MUST NOT reconstruct it by search nor infer it from the envelope; what remains in effect as knowledge is provided by memory and the artifacts, queried by topic. When it cannot establish what happened, it MUST declare that and consult the user, and MUST NOT fill the gap with what seems plausible. |
| PR-ORQ-25 | With an envelope that meets its contract, the convening agent MUST validate the envelope, read `AdditionalContext`, interpret `Result` as the attribution of cause it is, and relate both to the objective's state and to any new requirements before it proceeds. It decides how deeply to inspect `ExtraArtifacts` from the result, the context, the objective, and the risk: it MUST NOT set them aside without understanding them, and MUST NOT read them all mechanically. When available evidence does not let it decide, it tells the user what needs investigation or asks how to proceed. |
| PR-ORQ-26 | An envelope that does not meet its contract withdraws the convening agent's license to rely on it: it MUST verify artifacts, paths, memory entries, and context firsthand instead of trusting the summary or the declared references. |
| PR-ORQ-27 | On an anomalous return, reconcile transition and artifact evidence before relying on the result. Route a technical fault to bounded diagnosis or correction when the goal and permissions suffice. Consult the user when evidence cannot establish continuity or proceeding requires a value or authorization decision. |
| PR-ORQ-28 | An `Aborted` result arrives with no content to interpret: the convening agent MUST consult the user rather than infer or reconstruct what happened, MUST NOT attribute fault to the temporary holder or to itself, and MUST NOT let it feed any reasoning about degradation. On an `Outraged` result, the convening agent recognizes its own drift from the isolated incident and corrects course. |

### 1.3 Workflow Frameworks

| ID | Requirement |
| --- | --- |
| PR-ORQ-14 | A workflow framework is a supported reference for the software-development happy path, providing planning artifacts, theoretical support for decisions, and a shared way to understand progress. It is never the universal route for every kind of work. |
| PR-ORQ-15 | A framework's planning artifacts reduce uncertainty and reveal whether work is still being planned, is ready for implementation, or has produced verifiable results. Their availability informs orchestration decisions without imposing a predetermined route. |
| PR-ORQ-16 | A framework does not impose global serial planning or one route on unrelated task classes. Its local entry and exit conditions govern the adopted route; beyond them, sequencing follows real dependencies. |
| PR-ORQ-17 | A framework MAY recommend suitable specialists for a given objective, but the orchestrator remains responsible for selecting the actual execution route and participants according to the goal and current evidence. |
| PR-ORQ-19 | SDD plans incrementally to the next executable slice. Its cycle is, in order: lightweight specification; executable acceptance tests written blindly by the test author, with a failing baseline; implementation with local checks; independent functional end-to-end acceptance by the verifier; advisory review; and checkpoint commit. The slice's functional scope freezes when it starts; changes follow `PR-ORQ-35`. TPM supplies the slice's bounded work breakdown from the specification, acceptance criteria, and frozen interfaces; the orchestrator compiles the plan from which the execution DAG derives. This cycle governs integrated software features, not every task class. |
| PR-ORQ-20 | Independent bounded units may run without a baseline within the unplanned-delegation bound. A covering plan is committed before a dependent sequence or its newly discovered consumer. At the bound, the orchestrator commits valid coverage or stops delegation with the actual result. Plan coverage does not erase consumption or bypass slice limits. |
| PR-ORQ-29 | More than one workflow framework MAY be available for the same phase of work (planning or implementation). Where more than one is available, the orchestrator MUST select the active one for that phase through a documented, extensible selection criterion evaluated against the concrete scenario — never improvised per-case reasoning — such that adding a new framework extends the criterion without rewriting it for the frameworks already covered. |
| PR-ORQ-30 | Direct work is a named bounded route under `PR-ORQ-29`, not the absence of a framework. Autonomous selection retains the triviality tests. An explicit direct-work order permits nontrivial, multi-pass work within its scope, without expanding permissions, ownership or budgets; a generic implementation request does not. Task-wide no-delegation includes verification. Report direct checks as self-checks, not independent assurance. |
| PR-ORQ-31 | When an autonomously selected bounded route no longer fits, switch to a workflow framework without collapsing remaining work or seeking permission to correct that choice. For user-ordered direct work, complexity or multiple passes alone are not a mismatch. Material uncertainty, new scope, or a blocked path follow `PR-ORQ-5`; changing the user's instruction requires their decision. |
| PR-ORQ-32 | When no available route for a phase — bounded or any workflow framework — fits the evaluated scenario, the orchestrator MUST NOT force a fit or default silently to either extreme; it handles the gap under `PR-ORQ-5`. |
