# takt-ai chart

This chart runs Takt AI in one of two execution modes, selected at install time:

- `direct` (default): the chart deploys one disposable OpenCode v2 web workspace with Takt AI preinstalled. Each Helm release receives its own PVC; the optional repository checkout and OpenCode/Takt writable data live on that claim. Use a distinct release name for each workspace. The default is one replica; `replicaCount` remains configurable.
- `coder`: the chart installs the official [Coder](https://coder.com) server through its optional dependency and deploys no Takt workload of its own. Each person gets an isolated, persistent workspace provisioned from a template the operator publishes separately with the Coder CLI ([deploy/coder/README.md](../../deploy/coder/README.md)).

Direct mode serves OpenCode over HTTP with its built-in Basic Auth, always as the fixed user `opencode`. Coder mode authenticates people through the operator's OIDC provider, and OpenCode is reached through an owner-only Coder terminal; no Takt HTTP service is exposed. The chart implements no OIDC in front of direct mode, and placing an identity-aware gateway there is an operator's own choice outside this chart.

## Get the chart

Every release publishes the chart, versioned in lockstep with the image it deploys (`appVersion` = `docker.io/roucru/takt-ai` tag):

```sh
# OCI (signed with cosign)
helm install demo oci://ghcr.io/rou-cru/charts/takt-ai --namespace takt-workspaces

# Classic Helm repository (GitHub Pages)
helm repo add takt-ai https://rou-cru.github.io/takt-ai
helm install demo takt-ai/takt-ai --namespace takt-workspaces
```

With no image values set, the chart runs `docker.io/roucru/takt-ai:<appVersion>`.

## Execution modes

`execution.mode` (`direct` | `coder`, default `direct`) and `coder.enabled` (boolean, default `false`) select the mode together and must agree: `execution.mode=coder` exactly when `coder.enabled=true`. The values schema rejects either mismatch, an unknown mode, or a wrong type before anything renders.

In `coder` mode the chart's direct resources — Deployment, Service, NetworkPolicy, HTTPRoute, ExternalSecret, VPA, and the direct ServiceAccount — are all disabled; the release renders the upstream Coder resources instead. The direct PVC keeps its name and spec in both modes; in `coder` mode (or with `persistence.retain=true`) it carries `helm.sh/resource-policy=keep`, so enabling or upgrading Coder never deletes it. The claim is allocated in `coder` mode too (`persistence.size`, 10 GiB by default), even when no direct workspace runs — an explicit cost of keeping the switch back to direct mode reversible. No chart Pod mounts it in `coder` mode, so with a `WaitForFirstConsumer` StorageClass it stays `Pending`, and `helm install --wait` or `helm upgrade --wait` waits on it until the timeout: in `coder` mode use a StorageClass with `Immediate` binding for `persistence.storageClassName`, or install without `--wait`.

The chart never creates a Namespace, ClusterRole, or Coder user, and it never publishes a workspace template or stores a Coder credential. First-user bootstrap and template publication are operator actions outside Helm ([First user and template publication](#first-user-and-template-publication)).

## Dependency provenance

The optional dependency is the official `coder` chart, version 2.38.0, from `https://helm.coder.com/v2`, conditioned on `coder.enabled`. It is the chart's only direct dependency. `Chart.lock` pins the resolved dependency and is generated by `helm dependency build` (or `helm dependency update`) under normal TLS verification; it is tool-produced, never hand-written. Because the dependency is declared, `helm template` and `helm package` fail on a checkout whose dependency has not been fetched — register the Coder repository and resolve the dependency first:

```sh
helm repo add coder https://helm.coder.com/v2
helm dependency build charts/takt-ai
```

Release packaging and CI do the same before linting and packaging.

## Prerequisites

- Kubernetes nodes on `linux/amd64` or `linux/arm64`; the image is multi-arch. Use `nodeSelector` (for example `kubernetes.io/arch: arm64`) to pin a node pool.
- A namespace for the release. The chart renders no Namespace object; create it yourself or pass `--create-namespace`.
- A default StorageClass or `persistence.storageClassName` that provisions `persistence.size`. The direct PVC renders in both modes; choose a reclaim policy appropriate for disposable work.
- Gateway API `HTTPRoute` CRD and controller, only when `httpRoute.enabled=true` in direct mode.
- External Secrets Operator CRDs/controller and a SecretStore or ClusterSecretStore, only when `externalSecret.enabled=true` in direct mode.
- VPA CRD/controller, only when `vpa.enabled=true` in direct mode.
- Optionally, in direct mode, a Kubernetes Secret for OpenCode server authentication. The Secret name/key are references only; secret bytes are never chart values.
- In `coder` mode, the additional [Coder prerequisites](#prerequisites-in-coder-mode).

## Image

Releases publish `docker.io/roucru/takt-ai` (mirrored at `ghcr.io/rou-cru/takt-ai`) for `linux/amd64` and `linux/arm64`, signed with cosign and carrying SBOM and SLSA provenance attestations. The image is built by the `workspace` target of `deploy/images/Dockerfile`; it compiles Takt AI and installs/configures OpenCode and its Takt integration during the build.

To build your own instead:

```sh
# local image for the host platform
docker buildx bake workspace --set '*.platform=' --load

# publish to your registry
WORKSPACE_TAG=registry.example/takt-ai:custom VERSION=custom \
  docker buildx bake workspace --push
```

Override `image.repository` and `image.tag`, along with `image.pullPolicy` and optionally `image.pullSecrets`. Set `image.digest` (`sha256:...`) to pin the exact image; it takes precedence over `image.tag`.

In `coder` mode the same image is the workspace target: the template's `workspace_image` input references it by digest ([deploy/coder/README.md](../../deploy/coder/README.md)).

A `NetworkPolicy` is rendered by default (`networkPolicy.enabled`) in direct mode. It admits ingress only on the server port, from any peer unless `networkPolicy.ingressFrom` lists the allowed `NetworkPolicyPeer`s. Egress is left unrestricted, because the agent needs model providers, git remotes and package registries. Setting `networkPolicy.egress` to a list of rules enforces egress too, and an empty list (`[]`) denies all of it.

## Install, upgrade, and remove

```sh
helm install demo oci://ghcr.io/rou-cru/charts/takt-ai \
  --namespace <your-namespace> --create-namespace \
  --set server.passwordSecret.name=<your-opencode-auth-secret>
```

From a source checkout, fetch the dependency first: `helm repo add coder https://helm.coder.com/v2`, then `helm dependency build charts/takt-ai`.

```sh
helm upgrade demo oci://ghcr.io/rou-cru/charts/takt-ai \
  --namespace <your-namespace> -f <your-values-file>.yaml
helm uninstall demo --namespace <your-namespace>
```

Uninstall deletes the direct PVC unless `persistence.retain=true` or the `coder`-mode keep rule holds; the backing volume then follows the StorageClass reclaim policy (`Delete` or `Retain`), so verify it before hosting user data. Generic deployment helpers for the workspace image live in [deploy/workspace/](../../deploy/workspace/README.md); they are not part of this chart's install path and this guide does not use them.

## Repository checkout

When `workspace.repository.url` is omitted, the clone init container is omitted and OpenCode starts against the PVC. At startup, the image registers that directory as a project and creates one visible `Workspace` session if no unarchived session exists there; Pod restarts reuse the existing session. To clone a repository, configure URL and optional branch, tag, or commit revision:

```yaml
workspace:
  repository:
    url: https://github.com/example/project.git
    revision: main
    authSecret:
      name: private-git-credentials
      usernameKey: username
      passwordKey: token
```

The referenced Secret must exist in the release namespace and contain those keys. Do not put credentials in the repository URL or Helm values. The init container uses a temporary `GIT_ASKPASS` helper and removes it on exit; clone failure prevents the OpenCode container from starting. A restart with an already initialized `.git` checkout does not reclone or reset the user's changes. No-clone mode does not create a Git repository.

## Secrets

Create a Secret out-of-band, or set `externalSecret.enabled=true` and configure the External Secrets resource:

```yaml
externalSecret:
  enabled: true
  secretStoreRef:
    kind: ClusterSecretStore
    name: workspace-secrets
  target:
    name: demo-workspace-secrets
  data:
    - secretKey: password
      remoteRef:
        key: workspaces/demo/opencode
        property: password
server:
  passwordSecret:
    name: demo-workspace-secrets
    key: password
```

Alternatively omit chart ExternalSecret generation and reference a pre-existing Secret. Repository clone authentication and server password references are independent. Use `runtime.env` only for non-sensitive environment values; pass provider credentials with `runtime.envFrom` Secret references or other Kubernetes secret references. Rendered Helm resources contain references and remote SecretStore keys, never remote secret payloads. OpenCode v2 always requires Basic Auth with the fixed user `opencode`. `server.passwordSecret` supplies the password as `OPENCODE_PASSWORD`; without it, the entrypoint generates one and prints it once to the container log as `server password <value>`. Either way the server and every web-terminal PTY inherit it, so `opencode --server http://localhost:4096` works from the web terminal without extra input. The HTTPRoute itself does not require a password Secret.

## Networking and sizing

`httpRoute` is disabled by default and renders only Gateway API HTTPRoute (never Ingress). Set `parentRefs`, `hostnames`, `rules`, labels, and annotations as needed by the Gateway controller. The default route rule matches `/` and forwards to the workspace Service. OpenCode v2 serves its browser UI and API from the root path; path-prefix hosting is not guaranteed by this PoC.

`vpa` is disabled by default. If enabled, configure `updatePolicy` and `resourcePolicy` for the installed VPA version. Its default update mode is `Off` to avoid replacing an active interactive workspace automatically. `priorityClassName` optionally assigns a cluster PriorityClass to the workspace Pod. CPU/memory requests and limits, pod/container security contexts, probes, ServiceAccount behavior, image, command/args, env, and node placement are configurable.

Defaults target a restricted Pod Security baseline: non-root UID/GID 10001, `RuntimeDefault` seccomp, dropped Linux capabilities, `sa-<release>` ServiceAccount names (the chart name is appended when the release name does not contain it), Gateway API v1 HTTPRoute, and External Secrets Operator v1 with a namespaced SecretStore. Override Gateway parent references, store kind/name, labels, annotations, sync metadata, and VPA policy through values. Liveness/readiness/startup probes use TCP by default so HTTP Basic Auth does not make an HTTP probe fail; setting a probe's `path` switches that probe to HTTP GET.

## Ephemeral data and cleanup

The PVC stores the checkout and all runtime writes and is unique to each Helm release. It is mounted through sibling subPaths: `workspace` at the workspace mount, `data`, `state`, and `cache` at the Takt user's XDG directories (OpenCode data, the private VFS store, Engram memory, tool caches), and `tmp` at `/tmp`. Private state therefore persists with the workspace but never lives inside the workspace tree, which the VFS requires. Uninstall deletes the PVC by default; set `persistence.retain=true` to preserve the PVC object intentionally. In `coder` mode the claim always carries `helm.sh/resource-policy=keep` and survives uninstall. Even when a claim is deleted, actual backing PV deletion follows that StorageClass's reclaim policy (`Delete` or `Retain`); verify it before deploying user data. Git changes intended to survive should be pushed to the repository before deleting the workspace. S3/artifact export is outside this chart's scope.

## Coder mode configuration

Every Coder control-plane value is the upstream chart's own schema, passed through unchanged under `coder.coder.*`; the parent adds no second control-plane schema. This section records what the parent schema requires and what its defaults set — configure everything else through the upstream `coder` values.

### Required environment entries

In `coder` mode, `coder.coder.env` must contain each entry below with the given shape. The defaults supply no endpoint, secret reference, client ID, or credential; those values are yours.

| Entry | Shape |
| --- | --- |
| `CODER_PG_CONNECTION_URL` | `valueFrom.secretKeyRef` `name`/`key` to an existing Secret; a literal `value` is rejected |
| `CODER_OIDC_CLIENT_SECRET` | `valueFrom.secretKeyRef` `name`/`key` to an existing Secret; a literal `value` is rejected |
| `CODER_OIDC_ISSUER_URL` | Absolute HTTPS URL |
| `CODER_ACCESS_URL` | Absolute HTTPS URL |
| `CODER_OIDC_CLIENT_ID` | Non-empty string |
| `CODER_DISABLE_PASSWORD_AUTH` | Literal string `true` |
| `CODER_OAUTH2_PROVIDER_ENABLE` | Literal string `true` |

Env names must be unique: any name repeated anywhere in `coder.coder.env` fails the render, and the error names the repeated entry. Optional extra entries keep their upstream shapes and cannot replace a required entry. `envUseClusterAccessURL` is false, so `CODER_ACCESS_URL` is the only endpoint input. Register OIDC at your identity provider with Coder's callback path `/api/v2/users/oidc/callback`.

`CODER_DISABLE_PASSWORD_AUTH=true` disables password login for ordinary users. Coder keeps its documented Owner password exception: an Owner can still sign in with the owner password. That exception is authenticated upstream behavior, disclosed here, not an open bypass. `CODER_OAUTH2_PROVIDER_ENABLE=true` enables Coder's OAuth2 provider, which Backstage uses for per-user Coder authorization; registering that OAuth application and its callback is operator-side work ([deploy/coder/BACKSTAGE.md](../../deploy/coder/BACKSTAGE.md)).

### Provisioner permissions

Workspace provisioning is namespaced. The defaults set the minimum same-namespace profile: `coder.coder.serviceAccount.workspacePerms=true`, `enableDeployments=false`, and `extraRules` limited to `apiGroups=["networking.k8s.io"]`, `resources=["networkpolicies"]`, `verbs=["get","list","watch","create","update","patch","delete"]`. Upstream basic permissions already cover Pods and PVCs; the workspace template also creates a NetworkPolicy, so Pods-and-PVCs alone are insufficient. For a dedicated workspace namespace, set `workspacePerms=false` and list the namespace under `workspaceNamespaces` with the same profile. Entries inherit the top-level settings, so when the top level is `false`, each listed entry needs an explicit `workspacePerms: true` — an entry without it grants no workspace permissions in that namespace. The chart creates no Namespace or ClusterRole and adds no RBAC of its own. Workspace Pods run with the service-account token unmounted, and the provisioner's service account is never mounted into a workspace.

### Prerequisites in `coder` mode

- An existing namespace for the release, and a separate namespace for workspaces if you use a dedicated one.
- An external PostgreSQL database reachable from the cluster, referenced through `CODER_PG_CONNECTION_URL`.
- An OIDC provider registration for user authentication, with the callback path above.
- DNS and TLS routing for `CODER_ACCESS_URL`. The default Coder service is `ClusterIP`; `coder.coder.ingress.*` and `coder.coder.httproute.*` stay disabled until you configure them, and `coder.coder.tls.secretNames` terminates TLS at Coder when used that way.
- Storage, CNI enforcement, and workspace image access are template publication inputs, not chart values: see [deploy/coder/README.md](../../deploy/coder/README.md).

## First user and template publication

Two operator actions sit outside Helm:

1. **First user.** A fresh Coder server has no users. Create the first one with Coder's documented first-user workflow — the dashboard's first-login setup or `coder login` with its first-user flags — never through a chart value; the chart stores no bootstrap password. First-user bootstrap on an OIDC-only deployment with the exact Coder release is unverified; record the path you actually used.
2. **Template publication.** Publish the workspace template from `deploy/coder` with the Coder CLI (`coder templates push`); see [deploy/coder/README.md](../../deploy/coder/README.md). Publication is an explicit operator action, never a Helm upgrade side effect; a repeated push creates a new template version, and no exactly-once publication is claimed.

The chart's post-install notes report the selected mode and these prerequisites. They do not report a created or verified template: Helm readiness is not workspace readiness.

## Switching modes

A mode switch selects the execution system. It does not migrate a direct workspace into Coder, merge memory databases, or move data between claims.

**`direct` → `coder`:** set `execution.mode=coder` and `coder.enabled=true` together. The direct resources disappear from the release and the Coder control plane and its chart RBAC appear. The direct PVC is retained by the keep rule, so the earlier direct data is usable when you switch back. Terraform-managed workspace resources are not touched.

**`coder` → `direct`:** stop every workspace through Coder first. Otherwise live workspace Pods keep running, keep consuming resources, and lose control-plane connectivity; Helm does not clean them up. Then set `execution.mode=direct` and `coder.enabled=false`. The Coder dependency and its RBAC disappear; workspace PVCs, workspace records, and Coder's database are not deleted by the switch.

**Reactivating Coder:** reuse the same external PostgreSQL database, namespace, release identity, and template state, then start workspaces again explicitly. Keep backups of the database and volumes yourself: no switch preserves data after you delete the external database or volumes, and a PVC is not a backup.

Uninstalling the chart is not the mode-switch test. The documented acceptance sequence — `direct` → `coder` → `direct` → `coder`, with workspaces quiesced through Coder before Coder is disabled — is a procedure recorded in [deploy/coder/ACCEPTANCE.md](../../deploy/coder/ACCEPTANCE.md), not something this chart automates.

## Verification status

Render-time behavior in this README — mode coupling, env validation, resource gating, the retained claim, duplicate-name rejection — is covered by the repository's bounded chart regression (`development/testing/test-coder-chart.sh`), which also scans the repository's tracked source files for environment-specific literals (CW-T1-09). The regression exits 0 when every check passed, 1 when at least one check failed, and 3 when unverified checks remain — not a failed check; an unverified run means a missing helm or git, an unresolved Coder dependency, or an unavailable git baseline. The runner map is in [development/testing/README.md](../../development/testing/README.md). No live Coder deployment is exercised by product tests: first-user bootstrap, OIDC login, template import, workspace start, terminal access, and Backstage self-service are acceptance procedures whose evidence and current status live in [deploy/coder/ACCEPTANCE.md](../../deploy/coder/ACCEPTANCE.md). A successful `helm install` or a running Coder pod is not evidence of a working Takt workspace.
